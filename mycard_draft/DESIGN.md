# LINE 自動扣點操作設計

狀態：設計／離線草稿。尚未接上 MyCard、LINE 圖片處理或正式帳本，不能部署啟用。

## 管理員實際怎麼操作

1. 管理員在已設定的客人群貼 MyCard QR 圖。
2. 機器人解析圖，取得扣點頁／供應商交易資訊，回覆待扣資料：商品／收款對象、商品金額與幣別、實際扣點數。原圖、操作人與本群綁定，5分鐘有效；圖片本身不會扣點。
3. 管理員核對後傳 `扣點65`，表示授權這張 QR 的單筆65點交易，不需數量。`扣點3290` 同理。僅主管理員有效；一般拿卡成員無權扣點。
4. 機器人先鎖定這筆訊息、QR、群組額度與 MyCard 錢包，保存處理紀錄，再讀一次付款資訊。點數、交易金額、幣別、收款對象、訂單及QR識別都須與這筆已綁定資料一致，且未過期；一致才自動送出一次付款。成功流程不再要求另一個付款按鈕。
5. 供應商明確確認成功後，一次記帳並回覆扣點結果、供應商交易編號、記帳金額與群組帳況。這是扣點服務單，不取用卡片序號庫存。

## 65元圖片如何使用

已實際確認：上傳圖片可離線辨識，QR網址屬 www.mycard520.com，包含交易授權參數與加密交易資訊；未開啟該網址或呼叫MyCard介面。沒有輸出授權參數。

未實際確認：這張QR目前是否仍有效、交易頁是否為65元、實際扣點數是否65點、收款商品及帳號。65元是使用者提供資訊，不能代替供應商報價。

下列為設計畫面示例，非真實查詢結果：

> 待扣交易
>
> 商品金額：NT$65
>
> 實際扣點：65點
>
> 商品／收款對象：由交易頁取得
>
> 輸入「扣點65」後自動處理；本次只處理這一筆。

只有供應商回傳實際扣點為65點，才能使用 `扣點65`；不能將商品金額與扣點數混為同一欄。

## 自動記帳

保留三個不同數字：商品原交易金額、MyCard實際扣點數、向客人收取的售價。收款前先保存本筆折數與售價，原交易日及供應商交易編號保留。

扣點服務的折數與單筆上限須明確設定，目前未設定正式值。既有庫存拿卡價格不會被更改。若確認扣點也沿用0.905，65點的客人售價範例為58.83元；這只是算例，不是已記帳或已核定扣點售價。

額度計算包含預付款、已欠金額及所有未完成付款的保留額度。一般拿卡與扣點共用同一群帳戶檢查，避免同時操作各自用掉同一份額度。

## 異常會怎麼處理

| 情況 | 行為 |
|---|---|
| 點數、金額、幣別、對象或訂單變動 | 付款前拒絕，需重新核對；不付款、不記帳 |
| QR或指令過期 | 要求重新貼圖；不付款 |
| 同一LINE訊息重送 | 回覆既有處理狀態，禁止重新付款 |
| 同一QR由不同圖片或訊息重送 | 由持久化QR識別去重，不能重複付款 |
| 同帳號跨群同時扣點 | 錢包串行與群組額度保留，避免覆蓋待付款交易 |
| 查詢失敗，尚未送付款 | 結束這次嘗試，不付款、不記帳 |
| 已送出付款但逾時／結果不明 | 保留待核對，禁止自動重扣或假設失敗退款 |
| 付款成功但記帳失敗 | 保存供應商成功參照，只補記帳，不再付款 |
| 已付款卻輸入 `/撤回` | 不能只沖回帳款宣稱已退點；退款另依供應商方式核對 |

## 仍須完成的串接

- 已有的「API」實為使用者提供的瀏覽器外掛，沒有另一個平台或文件。須確認可用的受支援授權、交易查詢、付款及結果核對方式。不能直接以外掛App私有端點與內嵌金鑰推定雲端扣點已可用。
- 在支援的可信任登入／驗證流程完成同一個MyCard帳戶的授權，避免將密碼、支付密碼或OTP放進LINE聊天、GitHub或診斷日誌。
- 實作耐重啟的交易journal、共享額度保留與冪等記帳，並在隔離PostgreSQL做並發及中斷測試。現有流程測試使用模擬依賴，未驗證正式DB持久化或付款。
- 接上LINE圖片、受限QR解析、供應商報價及回覆卡片。不能把QR字串中的任意網址當成可存取的網路目標。
- 設定扣點售價、單筆上限、允許群組，再提出明確正式啟用改動與測試交易供使用者確認。現有圖片不代表已授權付款。

## 已做的離線驗證

36項模擬測試通過：指令格式、管理員／群組／圖片／時間綁定、頁面資訊完整性、付款前重新報價、金額／點數／收款對象變動、付款前後逾時、成功待補帳及去重介面呼叫順序等。

執行：`python -m unittest -q mycard_draft.test_flow mycard_draft.test_images`

這些測試沒有真實登入、扣點、群組記帳或LINE試發；實際串接尚未完成。
